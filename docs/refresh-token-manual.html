1Czy w systemie JWT nadal istnieje "sesja"?

Krótka odpowiedź: access token jest celowo bezstanowy (stateless) — ale refresh token celowo przywraca sesję.

Klasyczna sesja oznacza, że serwer trzyma stan: wiersz (albo wpis w pamięci) mówiący "sesja abc123 należy do użytkownika X, utworzona o czasie T, ważna do T+N". Klient trzyma tylko nieprzezroczyste odwołanie do niej (tradycyjnie ciasteczko w stylu connect.sid). Unieważnienie jest trywialne: usuń wiersz.

Podpisany JWT jako access token odwraca ten model. Sam token niesie w sobie dane (sub, exp, aud, ...) i sam się weryfikuje dzięki podpisowi — serwer nie trzyma żadnego stanu per-request. Właśnie dzięki temu access tokeny JWT są szybkie i skalują się horyzontalnie: dowolny serwis z kluczem publicznym może zweryfikować żądanie bez zapytania do bazy danych.

Koszt tej bezstanowości: nie da się unieważnić pojedynczego access tokenu przedwcześnie. Jest ważny aż do exp, kropka — chyba że zbudujesz listę odwołanych tokenów (blocklist), co niweczy cały sens "bezstanowości", po którą sięgnąłeś.

Access tokenRefresh token
Czas życiaKrótki (minuty)Długi (dni/tygodnie)
StanowośćBezstanowy (JWT)Stanowy — wiersz w bazie
Unieważnienie natychmiast?NieTak
Używany doAutoryzacji wywołań APIWydawania nowych access tokenów
Czyli tak — nadal powinieneś mieć "sesję". Jest ona tylko ograniczona do poziomu refresh tokenu, a nie access tokenu. Access token to krótkotrwała, jednorazowa zdolność wyprowadzona z tej sesji, wydawana na nowo co ~15 minut, dopóki sesja (refresh token) jest nadal ważna.

2Refresh token: opaque czy JWT?

Analogia

JWT = notatka, którą możesz sam odczytać. header.payload.signature — payload jest jedynie zakodowany w base64url, nie zaszyfrowany. Każdy, kto ma token, może go zdekodować i odczytać każdy claim bez żadnego wysiłku. Podpis dowodzi jedynie autentyczności/integralności, nie poufności. Weryfikacja to czysta kryptografia (sprawdzenie podpisu) — bez zapytania do bazy danych.

Token opaque = numerek z loterii. crypto.randomBytes(32) → coś w stylu k8F3...Qz1. To czysta entropia — nie koduje żadnej informacji o tym, do kogo należy ani kiedy wygasa. Jedyny sposób, by się czegoś o nim dowiedzieć, to sprawdzić go w rejestrze wydawcy (twojej bazie danych). Weryfikacja to zawsze zapytanie do bazy.

Porównanie wprost

JWT jako refresh tokenOpaque jako refresh token
FormatStrukturalny, samowystarczalnyLosowe bajty, bez struktury
WeryfikacjaSprawdzenie podpisu — bez DBZapytanie do bazy — zawsze
UnieważnienieTrudne (blocklist = i tak stan w bazie)Trywialne — oznacz wiersz
Co wycieka po kradzieżyWszystkie claimy — czytelne bez kluczaNic — nieodróżnialne od szumu
Księgowanie rotacjiWymaga jti + tabeli w bazie i takWiersz w bazie jest stanem rotacji
RozmiarWiększyMały, stały
Puenta: jeśli i tak potrzebujesz stanu w bazie — do unieważniania, rotacji, wykrywania reuse — to główna zaleta JWT ("bez zapytania do bazy") nic ci nie daje dla refresh tokenu. Płacisz za weryfikację podpisu, żeby odtworzyć coś, co i tak sprawdzisz w bazie, a w dodatku wyciekają czytelne claimy przy kradzieży.

Wniosek przyjęty w tym projekcie: access token → JWT (bezstanowa weryfikacja, krótkotrwały). Refresh token → losowy opaque, haszowany przed zapisem (jawne odwołanie do sesji, trywialna rotacja i unieważnianie).

// nigdy nie zapisuj surowego tokenu — tylko hash
const raw = crypto.randomBytes(32).toString("base64url");
const tokenHash = crypto.createHash("sha256").update(raw).digest("hex");
// raw -> trafia do klienta (cookie)
// tokenHash -> trafia do bazy danych

Tokeny opaque to dane losowe o wysokiej entropii, nie niskoentropijne sekrety jak hasła — dlatego szybki hash (SHA-256) wystarczy; hasła potrzebują wolnego, solonego hasha jak Argon2.

3Rotacja i wykrywanie ponownego użycia

Refresh token powinien być jednorazowy: wymiana go na endpointzie /auth/refresh natychmiast go unieważnia i wydaje zupełnie nowy. To rotacja refresh tokenów, i to właśnie ona umożliwia wykrywanie reuse.

sequenceDiagram participant Client participant API as /auth/refresh participant DB as Tabela RefreshToken Client->>API: ciasteczko refresh_token = T1 API->>DB: szukaj hash(T1) DB-->>API: wiersz znaleziony, revokedAt = null, nie wygasł API->>DB: oznacz T1 jako revoked, utwórz T2 (replacedByTokenId = T1) API-->>Client: Set-Cookie: refresh_token = T2 Note over Client,API: Później — napastnik ukradł T1 przed rotacją,
albo klient powtórzył żądanie ze starym T1 Client->>API: ciasteczko refresh_token = T1 (już użyty!) API->>DB: szukaj hash(T1) DB-->>API: wiersz znaleziony, revokedAt != null 🚨 REUSE API->>DB: unieważnij wszystkie tokeny z rodziny T1 API-->>Client: 401 — wymuś pełne ponowne logowanie

Dlaczego to wykrywa reuse

Każdy refresh token jest jednorazowy. W momencie wymiany jego wiersz zostaje oznaczony jako revokedAt. Jeśli ten sam surowy token zostanie przedstawiony ponownie, wyszukiwanie znajdzie wiersz, który jest już unieważniony — co może się zdarzyć tylko wtedy, gdy ten sam token miały dwie strony. Bezpieczny ruch: unieważnij całą "rodzinę" tokenów i wymuś ponowne logowanie.

Czym naprawdę jest "rodzina tokenów"

Wyobraź sobie rodzinę tokenów jako jeden ciągły bieg sztafetowy, zaczynający się od logowania. Każdy refresh token to jeden biegacz niosący pałeczkę przez chwilę, po czym przekazujący ją kolejnemu (rotacja). Drużyna — wszyscy biegacze od pierwszego do obecnego — to rodzina (familyId). Pałeczka (uwierzytelniona sesja użytkownika) jest ta sama przez cały bieg; zmienia się tylko to, kto ją aktualnie niesie. R1 → R2 → R3 → R4 to cała ta sama rodzina — jeden wiersz na rotację, wszystkie z tym samym familyId; replacedByTokenId pozwala przejść po łańcuchu do celów debugowania/audytu.

Dlaczego unieważnia się całą drużynę, a nie tylko oznaczonego biegacza: jeśli napastnik ukradł pałeczkę R3 po tym, jak już została przekazana do R4, a ty unieważniłbyś tylko R3, to R4/R5/R6... (wydane po kradzieży) też mogą być już skompromitowane — napastnik mógł użyć skradzionego tokenu, by wyrobić sobie nowy, zanim cokolwiek zauważyłeś. Jedyną bezpieczną reakcją jest zakończenie całej linii i wymuszenie zupełnie nowego logowania.

Prawdziwy niuans: niewinne race'y a prawdziwe ataki

"Każde ponowne użycie unieważnionego tokenu = kompromitacja" ma jeden przypadek fałszywie pozytywny: wiele kart tej samej aplikacji dzieli to samo ciasteczko refresh tokenu, ale ma osobną pamięć JS. Jeśli karta A wykona refresh (R1 → R2) ułamek sekundy przed tym, zanim karta B spróbuje użyć R1, serwer widzi "reuse" — nieodróżnialne od ataku — i wylogowałby użytkownika ze wszystkich kart bez realnego powodu.

Standardową mitygacją (Auth0, OAuth 2.0 rotation BCP) jest krótkie okno tolerancji na reuse: jeśli już obrócony token pojawi się ponownie w ciągu kilku sekund od rotacji, traktuj to jako niewinny race, nie atak. Zakres tej lekcji: okno tolerancji jest zaimplementowane w tym podstawowym podejściu — to tanie (jedno porównanie znaczników czasu) i mocno zmniejsza liczbę fałszywych alarmów.

Deduplikacja (klient) vs. okno tolerancji (serwer)

Deduplikacja (single-flight)Okno tolerancji

Są komplementarne: deduplikacja zmniejsza częstość race'a, okno tolerancji sprawia, że serwer jest wyrozumiały, gdy mimo wszystko się zdarzy.

Dlaczego rotować przy każdym wywołaniu, nie tylko blisko wygaśnięcia

Wykrywanie reuse działa tylko dlatego, że każdy token jest jednorazowy. Gdyby ten sam token pozostawał ważny przez cały TTL (np. 30 dni), skradziony token byłby nieodróżnialny od prawowitego przez cały ten czas. Rotacja zmienia pytanie z "czy to w ramach TTL?" na "czy ta wartość była już użyta?" — wykrywając kompromitację w sekundy, nie miesiące. Wygaśnięcie i rotacja to osobne mechanizmy: wygaśnięcie ogranicza zewnętrzny czas życia rodziny; rotacja zachodzi przy każdej pojedynczej wymianie.

3aKiedy wywoływać /auth/refresh?

Nie jest wywoływany przed każdym użyciem access tokenu — access token jest dołączany bezpośrednio do każdego wywołania API (Authorization: Bearer ...) i weryfikowany wyłącznie podpisem, bez zapytania do bazy. Podczas 15 minut normalnego użycia, /auth/refresh jest wywoływany zero razy.

MomentDlaczego
Start aplikacji / odświeżenie stronyAccess token w pamięci zniknął; ciasteczko refresh przetrwało
Proaktywnie, przed expOdśwież wcześniej (np. ~12. minuta), żeby uniknąć widocznego błędu
Reaktywnie, przy 401Zabezpieczenie: wywołanie → 401 → refresh → ponów żądanie

Race condition dotyczy tylko wąskiego okna przypadku reaktywnego, gdy kilka żądań dostaje 401 naraz.

Rekomendacja w tym projekcie: access token trzymany tylko w pamięci (nigdy nie persystowany); przy pełnym odświeżeniu strony aplikacja po cichu wywołuje /auth/refresh. Refresh token: ciasteczko httpOnly, Secure, SameSite=Lax — niewidoczne dla JS.

Ochrona CSRF typu double-submit dla endpointów refresh/logout jest celowo oznaczona jako kolejny krok na przyszłość, nie zaimplementowana w tym podstawowym podejściu.

5onRequest vs preHandler w Fastify

onRequest → preParsing → preValidation → (walidacja body/query) → preHandler → handler
HookPrzed czym się wykonujeTypowe zastosowanie
onRequestParsowaniem body, walidacjąObecność nagłówka auth, rate limiting, CORS, logowanie
preHandlerHandlerem, ale po walidacji schematuSprawdzenia autoryzacji korzystające z request.body

Dlaczego authGuard jest preHandler, a nie onRequest: nie potrzebuje body, ale preHandler to konwencjonalne miejsce na "czy to żądanie ma prawo dotrzeć do handlera", zostawiając onRequest wolny na sprawy przekrojowe jak rate limiting.

6Pełny obraz — diagram cyklu życia tokenów

Łącząc poprzednie sekcje w jedną oś czasu, obejmującą całą sesję logowania:

sequenceDiagram participant FE as Frontend (pamięć) participant API participant DB as Tabela RefreshToken FE->>API: POST /auth/login (email+hasło) API->>DB: utwórz wiersz RefreshToken (rodzina F1) API-->>FE: access_token (JWT, 15m) + Set-Cookie refresh_token=R1 (httpOnly) Note over FE: access_token trzymany tylko w pamięci loop normalne użycie API (< 15 min) FE->>API: GET /resource (Authorization: Bearer access_token) API-->>FE: 200 OK (sprawdzony podpis + exp, bez zapytania do bazy) end alt proaktywny refresh (~12. minuta) FE->>API: POST /auth/refresh (cookie R1) API->>DB: R1 ważny i nieodwołany -> unieważnij R1, utwórz R2 (rodzina F1) API-->>FE: nowy access_token + Set-Cookie refresh_token=R2 else reaktywny refresh (access token już wygasł) FE->>API: GET /resource (wygasły access_token) API-->>FE: 401 Unauthorized FE->>API: POST /auth/refresh (cookie R1) API->>DB: rotacja R1 -> R2 API-->>FE: nowy access_token + Set-Cookie refresh_token=R2 FE->>API: ponów GET /resource (nowy access_token) API-->>FE: 200 OK end Note over FE,DB: ...mija czas, kolejne rotacje: R2 -> R3 -> R4... alt użytkownik się wylogowuje FE->>API: POST /auth/logout (cookie Rn) API->>DB: unieważnij Rn (opcjonalnie całą rodzinę F1) API-->>FE: 204, Set-Cookie refresh_token=(wyczyszczone) Note over FE: usuń też access_token z pamięci else refresh token w końcu wygasa (długa nieaktywność) FE->>API: POST /auth/refresh (cookie Rn, minął expiresAt) API-->>FE: 401 -> przekierowanie do logowania else wykryto reuse (skradziony/powtórzony stary token) FE->>API: POST /auth/refresh (cookie z już unieważnionym tokenem) API->>DB: znaleziony, ale revokedAt != null -> unieważnij całą rodzinę F1 API-->>FE: 401 -> wymuś pełne ponowne logowanie end
Na co zwrócić uwagę: access token nigdy nie dotyka bazy danych (czyste sprawdzenie podpisu); refresh token jest jedyną rzeczą trafiającą do /auth/refresh i każde udane użycie zastępuje samo siebie w tej samej familyId; historia refresh tokenu kończy się zawsze jednym z trzech sposobów: wylogowanie, naturalny expiresAt, albo unieważnienie całej rodziny po wykryciu reuse.

7Szybkie podsumowanie

  • Sesja nadal istnieje — żyje na poziomie refresh tokenu, nie access tokenu.
  • JWT = samowystarczalny, czytelny, bez zapytania do bazy. Opaque = bez znaczenia sam w sobie, zawsze zapytanie do bazy, trywialnie unieważnialny.
  • Access token → JWT. Refresh token → opaque, haszowany przy zapisie.
  • Rotacja = jednorazowe tokeny, przy każdej wymianie (nie tylko blisko wygaśnięcia). Reuse detection = unieważniony token użyty ponownie → unieważnij całą rodzinę (z oknem tolerancji na race'y między kartami, zaimplementowanym po stronie serwera).
  • /auth/refresh wywoływany tylko w konkretnych momentach (start, proaktywnie, reaktywnie) — nigdy przed każdym wywołaniem API.
  • Wygaśnięcie stałe vs. przesuwne to świadomy wybór produktowo-bezpieczeństwowy.
  • Access token: pamięć. Refresh token: ciasteczko httpOnly.
  • onRequest = najwcześniej, bez body. preHandler = po walidacji.
