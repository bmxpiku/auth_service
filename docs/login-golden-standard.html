Golden Standard: Login with Access & Refresh Tokens

A concise, opinionated blueprint for building a secure, modern login flow using short-lived JWT access tokens and rotating, DB-backed refresh tokens.

1Core Principles

  • Two tokens, two jobs. The access token proves identity for API calls; the refresh token exists only to obtain new access tokens.
  • Short-lived access, long-lived refresh. Access tokens expire in minutes; refresh tokens in days/weeks.
  • Stateless access, stateful refresh. Access tokens are verified by signature only (no DB lookup). Refresh tokens are opaque and checked against the database on every use.
  • Never store secrets in plaintext. Refresh tokens are hashed before being stored, exactly like passwords.
  • Rotate on every use, detect reuse. A refresh token is single-use. Presenting an already-used one is treated as a theft signal.
  • Transport matters as much as content. Delivery mechanism (cookie vs header) determines your XSS/CSRF exposure.

3. The Golden Flow

  1. Login — client sends email/password. Server verifies credentials with a constant-time check, generating a generic error on any failure (never reveal whether the email exists).
  2. Issue — on success, server creates a new token family: one access token (returned in body) + one refresh token (hashed & stored, raw value set as httpOnly cookie).
  3. Use — client attaches the access token to API calls until it expires.
  4. Refresh — when the access token expires, client calls /auth/refresh. The cookie carries the refresh token automatically. Server verifies it, marks it revoked, issues a brand-new access + refresh pair in the same family.
  5. Reuse detection — if a refresh token that is already marked revoked is presented again, the server assumes the token was stolen and revokes the entire family, forcing full re-login.
  6. Logout — client calls /auth/logout; server revokes the current refresh token and clears the cookie.

4. Security Checklist

Do

  • Hash refresh tokens before storing (argon2/sha256)
  • Rotate refresh tokens on every use
  • Detect & react to refresh token reuse
  • Use httpOnly + Secure + SameSite cookies
  • Return generic "invalid credentials" errors
  • Rate-limit the login endpoint per IP
  • Keep access tokens short-lived (≤ 15 min)
  • Sign JWTs with a strong secret / asymmetric key

Avoid

  • Storing refresh tokens as JWTs (defeats instant revocation)
  • Storing raw refresh tokens in the database
  • Putting refresh tokens in localStorage
  • Long-lived access tokens (hours/days)
  • Reusable refresh tokens (no rotation)
  • Leaking "user not found" vs "wrong password" distinctly
  • Skipping expiry/revocation checks on refresh

5. Minimal Data Model

RefreshToken {
  id                 string (uuid)
  tokenHash          string   // hash of the raw token, never the raw value
  userId             string   // FK -> User
  familyId           string   // groups all tokens issued from one login
  expiresAt          datetime
  revokedAt          datetime | null
  replacedByTokenId  string | null
  createdAt          datetime
}
