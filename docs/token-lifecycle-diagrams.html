Token Lifecycle Diagrams

Sequence, state, and flow diagrams covering every token-related operation: creation, rotation, reuse detection, revocation, and the end-to-end picture.

1Login — Token Creation

A new token family is created: one access token (stateless) and one refresh token (hashed & persisted).

sequenceDiagram
    participant C as Client
    participant S as Server
    participant DB as Database

    C->>S: POST /auth/login (email, password)
    S->>DB: findUnique(email)
    DB-->>S: user or null
    S->>S: verifyPassword (constant-time, argon2)
    alt invalid credentials
        S-->>C: 401 Invalid credentials (generic)
    else valid credentials
        S->>S: sign access token (JWT, exp 10m)
        S->>S: generate refresh token (random) and hash it
        S->>DB: insert RefreshToken (hash, userId, familyId, expiresAt)
        DB-->>S: ok
        S-->>C: 200 OK - accessToken in body, refreshToken cookie (httpOnly, Secure, SameSite=Strict)
    end

2Refresh — Rotation

Every refresh call retires the old refresh token and mints a brand-new pair in the same family.

sequenceDiagram
    participant C as Client
    participant S as Server
    participant DB as Database

    C->>S: POST /auth/refresh (cookie: refreshToken)
    S->>S: hash(incoming refresh token)
    S->>DB: findUnique(tokenHash)
    DB-->>S: token row
    alt not found, expired, or revoked
        S-->>C: 401 Unauthorized (re-login required)
    else valid and unused
        S->>DB: mark row revoked, set replacedByTokenId
        S->>S: sign new access token
        S->>S: generate new refresh token and hash it
        S->>DB: insert new RefreshToken (same familyId)
        DB-->>S: ok
        S-->>C: 200 OK - new accessToken in body, new refreshToken cookie
    end

3Reuse Detection — Theft Response

Presenting a refresh token that was already rotated/used is treated as a compromise signal: the whole family is revoked.

sequenceDiagram
    participant Attacker
    participant S as Server
    participant DB as Database
    participant Victim as Legit User

    Note over Victim,S: Token already rotated once (step 2)
    Attacker->>S: POST /auth/refresh (stolen, already-used refresh token)
    S->>DB: findUnique(tokenHash)
    DB-->>S: token row (revokedAt is not null)
    S->>S: reuse detected
    S->>DB: revoke ALL tokens where familyId matches
    DB-->>S: ok
    S-->>Attacker: 401 Unauthorized
    Note over Victim: next refresh also fails, must log in again

4Logout — Explicit Revocation

Logout revokes only the current token and clears the cookie; the rest of the family (other devices) stays valid.

sequenceDiagram
    participant C as Client
    participant S as Server
    participant DB as Database

    C->>S: POST /auth/logout (cookie: refreshToken)
    S->>S: hash(refresh token)
    S->>DB: update RefreshToken set revokedAt = now()
    DB-->>S: ok
    S-->>C: 204 No Content - cookie cleared (Max-Age 0)

5Token State Machine

Lifecycle states a single refresh token row can be in.

stateDiagram-v2
    [*] --> Active: created at login or rotation
    Active --> Rotated: used successfully at refresh
    Active --> Revoked: logout or manual revoke
    Active --> Expired: expiresAt passed
    Rotated --> ReuseDetected: presented again after rotation
    ReuseDetected --> FamilyRevoked: cascade revoke entire family
    Revoked --> [*]
    Expired --> [*]
    FamilyRevoked --> [*]

6End-to-End Overview

How the three endpoints and the database interact across a session's lifetime.

flowchart TD

    B --> C[POST /auth/refresh]

    D --> E[POST /auth/logout]
